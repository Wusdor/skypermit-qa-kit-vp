# ui-test-case-creator

Вход: `$ARGUMENTS`. Найти в нём JSON-объект от `/jira-intake` (`key`, `title`, `check_type`, `acceptance_criteria`, `confluence_url`, `notes`); посторонний текст до и после блока json игнорировать. Jira не читать.

Если `check_type` не `"ui"` (включая `null` и `"api"`) — вывести одну строку и остановиться: «не UI-задача, для API будет отдельный генератор». Если JSON не найден или `acceptance_criteria` пуст — одна строка с причиной, файлов не создавать.

Один кейс — один сквозной UI-сценарий (E2E) через форму и `data-testid`, с одним ожидаемым результатом. Формат и правила полей — как в `test-case-creator` (§5–§6): прочитай `.claude/skills/test-case-creator/SKILL.md` и примеры в `examples/`, чтобы не разойтись со стилем. Здесь описано только то, что отличается.

## 1. Источники

- **Ожидаемый результат — только Confluence SPD** (`cloudId` `f13593f8-183f-4502-ba93-6d6babaac436`, `getAccessibleAtlassianResources` не вызывать, `contentFormat: markdown`, чтение через `getConfluencePage` по ID; `searchConfluenceUsingCql` — только если страницы нет в таблице).

  | Страница | ID |
  |---|---|
  | 01 — Data Model | 229395 |
  | 02 — State Machine | 458753 |
  | 03 — API Contract | 491521 |
  | 04 — Frontend Spec | 524289 |
  | 05 — Open Questions | 360450 |
  | 06 — Business Rules | 491542 |
  | 07 — Clarifications | 557057 |
  | 08 — UML Diagrams | 589825 |

  Всегда читай «04», «05», «07», а также «01», «02», «06» по сути критериев. «05» — единственный источник статуса вопросов; «07» главнее «06».
- `test-plans/open-questions.md` — реестр `OQ-NN`.
- Код `../skypermit` — только для поиска селекторов и как oracle. Поведение по коду не становится ожидаемым результатом; если оно важно, укажи его в Rationale с пометкой «по коду, требует подтверждения» и путём `file:line`.
- В `../skypermit` ничего не менять. Значения из `OH-1` v1.4 и `CR-1` не использовать.

## 2. Селекторы

- Только `data-testid`. Находи `Grep`-ом в `../skypermit/app` и `../skypermit/components` (`data-testid`), в кейсе приводи значение и место: `` `aircraft-create-error` — app/operator/aircraft/page.tsx:144 ``.
- Динамические значения (`aircraft-registry-row-${a.id}`) записывай как шаблон с пояснением, что подставляется.
- У нужного элемента нет `data-testid` → так и пиши в Steps/Expected result («у элемента нет `data-testid`»), селектор не придумывай и не заменяй на CSS/текст. Если контракт `data-testid` описан в «04 — Frontend Spec», а в коде его нет (или наоборот) — отметь расхождение в Rationale.

## 3. Покрытие и техники

Каждый acceptance criterion покрыт хотя бы одним кейсом; критерий, который нельзя проверить через UI (нет элемента, нет такого экрана), попадает в `skipped` с причиной. У каждого кейса поле **«Техника»** — одна или несколько из:

- **EP** — классы эквивалентности: по одному кейсу на допустимый и недопустимый класс (уровень авторизации оператора, рейтинг пилота, весовая категория, зона).
- **BV** — граничные значения: время (`window_start` относительно «сейчас», curfew), вес (`mtom_grams`), длительность окна. Каждая сторона границы — отдельный кейс: на границе, на единицу ниже, на единицу выше.
- **State transition** — состояние заявки до и после действия (например, `DRAFT` → `SUBMITTED`-транзиент → `APPROVED` / `REJECTED`), легальные и нелегальные переходы по «02».

Не раздувай набор: техника применяется там, где критерий её допускает. Дубли существующих `E2E-*` кейсов не создавать — назвать существующий ID в `skipped`.

## 4. Предусловия E2E — полные

Перечисли всё, что нужно для прохождения сценария, и у каждого пункта дай ссылку на правило («06 — Business Rules» §…, «01 — Data Model» §…; номер раздела найди в странице, не угадывай):

- **Оператор:** `status = ACTIVE`, `authorisation_level` ≥ требуемого зоной.
- **Пилот:** рейтинг, достаточный для весовой категории борта и зоны, и действующая сертификация на `window_start`.
- **Борт:** `mtom_grams` / весовая категория — конкретное значение.
- **Зона:** код из «06» §4.
- **Заявка:** состояние `DRAFT`, поля и окно полетов (в формате «`T` = момент шага, `window_start` = `T + …`»).
- Подготовка, возможная через API, — через API; прямая запись в БД — только с пометкой «эндпоинта нет».

## 5. ID и файл

Формат `E2E-{ROLE}-{NNN}`: `OPR` — оператор (портал оператора), `REV` — рецензент (очередь рецензента). `NNN` — три цифры, `max + 1` по всем файлам `test-cases/*/E2E-{ROLE}-*.md` (`Glob`), как в `test-case-creator` §4; в пределах запуска номера подряд. Перед записью убедись, что такого ID нет ни в одной папке. История git этому скиллу недоступна (нет `Bash`), поэтому удалённые ранее ID он не увидит: не переиспользуй ID, о которых знаешь, что они удалены.

Один файл на кейс: `test-cases/e2e/E2E-OPR-NNN.md`. Заголовки полей — на английском, текст — на русском; идентификаторы из документации не переводятся. Порядок полей:

```markdown
# {ID}: <что проверяем, одной строкой>

- **ID:** {ID}
- **Jira:** <KEY>
- **Doc ref:** «<страница>» §<раздел>[; …][; OQ-NN]
- **Role(s):** <актор шага; кто ещё участвует в предусловиях>
- **Техника:** <EP | BV | State transition — с пояснением, какой класс/граница/переход>

## Preconditions
- <оператор, пилот, борт, зона, заявка в DRAFT — каждый пункт со ссылкой на правило>

## Steps
1. <действие в UI: страница, поле/кнопка и их `data-testid` с `file:line`>

## Expected result
<один наблюдаемый результат в UI или состояние заявки; каждое утверждение трассируется к Doc ref>

## Rationale
<какой acceptance criterion, какое правило, какая техника; расхождения «04»/код; «по коду, требует подтверждения: <file:line>»>

## Test data
| Параметр | Значение | Почему это значение |
|---|---|---|

## Status
Untested
```

Expected result безусловный (без «если…, то», «или»), кроме Blocked-кейсов.

## 6. Документация молчит

Ожидаемый результат не описан в SPD, вопрос открыт по «05» или «07» и «06» расходятся неразрешимо → кейс создаётся, но:

- Expected result: «Не определено — OQ-NN» и коротко, между чем выбор; ответ не подставляется ни по аналогии с другими экранами/эндпоинтами, ни из кода (поведение кода — только отдельной строкой «по коду, требует подтверждения: `file:line`» в Rationale).
- Status: `Blocked — OQ-NN`; в выводе `"blocked": true`.
- Нужного вопроса нет в `test-plans/open-questions.md` → добавь строку в таблицу реестра: следующий номер `OQ-NN`, обе стороны с цитатами, статус «Кандидат», колонка «Планы» — `TC e2e`. Существующие строки не менять, ID не переиспользовать.

Новые кейсы получают только `Untested` или `Blocked — OQ-NN`.

## 7. Проверка перед сохранением

- Каждый criterion — в кейсе или в `skipped`.
- Во всех Steps селекторы — только найденные `data-testid` с `file:line`; нет `data-testid` — так и сказано.
- У каждого кейса заполнены «Jira» и «Техника»; Preconditions полные и со ссылками.
- Expected result трассируется к Doc ref; ничего не взято по аналогии или из кода.
- Blocked-кейсы ссылаются на `OQ-NN`, который есть в реестре.

## 8. Вывод

Один блок json и ничего вне его:

```json
{
  "key": "SKY-1",
  "files": ["test-cases/e2e/E2E-OPR-001.md"],
  "cases": [
    {"id": "E2E-OPR-001", "title": "…", "technique": "BV", "blocked": false}
  ],
  "skipped": ["<критерий> — <причина>"]
}
```

`skipped` — `[]`, если пропусков нет. Новые строки реестра в блок не входят: они видны в `git diff` `test-plans/open-questions.md`.
