# api-test-case-creator

Вход: `$ARGUMENTS`. Найти в нём JSON-объект; посторонний текст до и после игнорировать.

- Обязательны: `gate`, `rule_reference`.
- Необязательны: `condition`, `story` (ключ Jira), `acceptance_criteria` (список из `jira-intake`), `covered_by` (пути к уже существующим кейсам на это правило).

Нет `gate` или `rule_reference` — ничего не писать, вернуть `{"status":"blocked","reason":"неполный вход"}`.

Один кейс — один проверяемый исход одного условия правила, запросами к `/api/v1`. Автотесты, коллекции и UI не затрагиваются.

## 1. Источники — только Confluence SPD

`cloudId` `f13593f8-183f-4502-ba93-6d6babaac436` (`getAccessibleAtlassianResources` не вызывать), `getConfluencePage` с `contentFormat: markdown`, по ID:

| Страница | ID | Что брать |
|---|---|---|
| 02 — State Machine | 458753 | таблица переходов, легальные и нелегальные переходы (для ST) |
| 03 — API Contract | 491521 | эндпоинты, методы, поля запроса, auth, коды, тело `422` |
| 06 — Business Rules | 491542 | условие правила (§1), `rule_reference` (§6) |
| 07 — Clarifications | 557057 | поправки к 06; при расхождении действует 07 |

ID не открывается — `searchConfluenceUsingCql` (`space = SPD AND title ~ "03"`). Дополнительно читать `test-plans/open-questions.md` — реестр `OQ-NN`; ссылаться только на вопросы, которые там есть.

`../skypermit` (docs, код, `openapi.yaml`) не читать. Эндпоинт, поле или код, которых нет в 03, не использовать; кейсы, которые без них не написать, — в `skipped` с причиной. Если ни одной страницы Confluence не открыть и поиск не помог — `blocked`. Не брать статус-код или формат ответа по аналогии с соседними эндпоинтами.

Формат — как у эталона `test-cases/gates/API-OPR-001.md`: прочитать его перед записью.

## 2. ID и файлы

- ID — `API-OPR-NNN`: максимум по всему `test-cases/` (`Grep` по `\bAPI-OPR-\d{3}\b`) + 1; кейсы получают номера подряд в порядке BV → EP → ST.
- ID не переиспользуются, даже если кейс когда-то удалили.
- Один кейс — один файл `test-cases/api/<ID>.md`. Существующие файлы не править и не перезаписывать; файл с таким именем уже есть — взять следующий свободный ID.
- Язык — русский; идентификаторы из документации (поля, статусы, эндпоинты, коды гейтов) не переводить.

## 3. Атомарность

- Ломается только условие правила из входа. Ранние гейты (`PILOT → AIRCRAFT → ZONE`) и остальные условия того же гейта заведомо проходят; скажи об этом в Preconditions.
- Новый оператор всегда `L1` (`authorisation_level` не поле регистрации, 03). Основа: зона `OPEN` без curfew, доступная `L1`; пилот и борт подходят зоне. Основу, требующую `L2`/`L3`, через API не построить — кейс в `skipped` с причиной.
- Один ожидаемый исход на кейс.
- `DRAFT` создаётся внутри кейса непосредственно перед проверкой. `window_start` задаётся относительно момента проверки `T` (как в `API-OPR-001`), а не абсолютной датой.
- Точка отсчёта lead time не определена (OQ-20). Кейс не должен от неё зависеть: между созданием `DRAFT` и проверкой проходят секунды, поэтому значения ставятся не ближе минуты к границе.

## 4. Техники — вывести набор

Только кейсы, которые техника даёт для ЭТОГО правила. Без комбинаций с условиями других гейтов, без двух кейсов на одно значение или класс. Техника, которая правилу не подходит (нет порога — нет BV), — в `skipped` с причиной.

- **BV.** Для каждого числового порога: на шаг ниже и на шаг выше (минута для времени), каждый — отдельный кейс, одиночная проба. Сама граница: если через API её нельзя проверить детерминированно (время между созданием `DRAFT` и проверкой сервером — секунды), она в `skipped` с этой причиной.
- **EP.** По одному представителю на каждый допустимый и недопустимый класс. Значение, прямо названное в `acceptance_criteria` (например, 6 ч 30 мин в AC5), всегда даёт отдельный кейс, даже если его класс уже покрыт BV-кейсом: BV проверяет границу, критерий — обещание задачи, трассировка AC → кейс. Класс, который уже закрыт BV-кейсом и которого критерии не называют, пропустить.
- **ST.** Цепочки запросов от свежего `DRAFT`, одна проверяемая смена состояния на кейс:
  - `validate` → `GET`: заявка осталась `DRAFT`; между шагами — предохранитель: ответ `validate` подтверждает провал (`422`, `failing_gate` по критерию), иначе кейс зелёный и при пройденном гейте;
  - `submit` → `422`;
  - `submit` → `GET`: `REJECTED` с `failing_gate`, `rule_reference`, `rejection_reason`;
  - повторный `submit` из `REJECTED` → `409`.

  Шаги-подготовки повторяются внутри кейса, без ссылок на другие кейсы. Легальность перехода сверять с 02.

### Пробы BV и EP: validate или submit → GET

- **Код ответа задан критерием** (`acceptance_criteria` прямо называет код) — проба `validate`, ассертить код из критерия. Правило раздела 6.
- **Код не задан ни в критерии, ни в 03** (код успешного `validate` в 03 не задан; OQ-23) — исход проверять через `submit` → `GET`:
  - сторона нарушения: `GET` даёт `state = REJECTED`, `failing_gate` = `<GATE>`, `rule_reference` = `<rule_reference>`;
  - сторона прохода: `GET` даёт точное состояние из таблицы переходов 02 для случая «все гейты пройдены» (взять из 02, не «не `REJECTED`» и не по памяти).

  В Rationale объяснить: почему не `validate` (dry-run, после него всегда `DRAFT`, различить проход и провал по `GET` нельзя; код успешного `validate` в 03 не задан); что заявка после `submit` остаётся в очереди ревьюера (на стороне прохода) и это ожидаемо.

## 5. Покрытие и `covered_by`

- Прочитать все файлы из `covered_by`. Кейс с тем же значением и тем же исходом не создавать: в `skipped` — «покрыто <ID>».
- Каждый criterion из `acceptance_criteria` — в кейсе или в `skipped` с причиной. Критерий, не проверяемый через `/api/v1`, — в `skipped`.

## 6. Код ответа и тело 422

- Confluence противоречит сам себе (OQ-07 для `submit`, OQ-23 для `validate`), а критерий задачи прямо задаёт код — ассертить код из критерия. В Rationale сослаться на критерий («SKY-2 AC2») и на 03, отметить противоречие с 08 ссылкой на OQ.
- Критерия нет — код не ассертить, исход проверять через `GET` (как в `API-OPR-001`).
- `422`: `failing_gate` = `<GATE>`, `rule_reference` — из 06 §6 с поправками 07, `message` — непустая строка, текст не проверять.
- Ничего сверх этого: другие гейты, заголовки, содержимое списков не ассертить.

## 7. Steps, Preconditions, Test data

- Steps — только HTTP-запросы к `/api/v1`: метод, путь, тело (поля по 03). `Auth` — ровно одно из «operator session», «X-Reviewer-Id», «none». `operator_id` не отправлять. Никаких `data-testid`, UI, браузера.
- Preconditions: оператор зарегистрирован `POST /api/v1/operators`, клиент держит session cookie; сущности — по свойству, с вызовом API, который их создаёт; у борта нет других заявок (overlap не срабатывает); условие «окно не на смене DST» — только для правил, где важно время зоны (curfew); для lead time не добавлять: он считается в UTC (`01` §Time handling), переход на летнее время на него не влияет.
- Test data — без email, имён, `national_id`, серийников, UUID и дат; только относительные значения (`T + 6 ч 01 мин`, `T − 30 дней`). Зону называть кодом, только если правило зависит от её параметров.

## 8. Формат файла

```markdown
# <ID>: <заголовок — что проверяем, одной строкой>

- **ID:** <ID>
- **Doc ref:** `06-business-rules.md` §<раздел>, §6; `03-api-contract.md` #<эндпоинт>; [`02-state-machine.md` таблица переходов — для ST]; [OQ-NN]
- **Technique:** <BV | EP | ST> — <значение / класс / переход>
- **Role(s):** <Оператор | Рецензент | Оператор → Рецензент>

## Preconditions
- <оператор, пилот, борт, зона — по свойствам, с вызовом API>
- <единственное нарушенное условие относительно порога; всё остальное в пределах>

## Steps
1. `<METHOD> /api/v1/<path>`. Auth: <operator session | X-Reviewer-Id | none>.
   Body: <поле> = <относительное значение>, …
   Save `id` как {{<имя>}}.
2. …

## Expected result
<один исход; каждое утверждение трассируется к Doc ref>

## Rationale
<почему кейс есть; правило, техника, критерий (story + AC), OQ; почему не validate — если применимо>

## Test data
| Параметр | Значение | Почему это значение |
|---|---|---|

## Status
Untested
```

Doc ref в `Doc ref` — имена страниц как в эталоне (`06-business-rules.md` и т. д. означают страницы Confluence с тем же номером), с номером раздела, найденным на странице, а не угаданным. Ожидаемый результат безусловный (без «если…, то»).

## 9. Документация молчит

Ожидаемый результат не определён вовсе (вопрос открыт по 05, 07 и 06 неразрешимо расходятся) — кейс создаётся, но: Expected result — «Не определено — OQ-NN» с кратким указанием, между чем выбор, без подстановки по аналогии; Status — `Blocked — OQ-NN`. `OQ-NN` должен быть в `test-plans/open-questions.md`; нужного вопроса там нет — этот кейс не писать, а добавить в `skipped`: «нужен новый OQ: <формулировка вопроса, источник A vs источник B>» (редактировать реестр этому скиллу нельзя). Остальные кейсы пишутся как обычно, `Untested`. Весь запуск `blocked` — только когда не хватает входа (`gate`/`rule_reference`) или Confluence недоступен.

## 10. Проверка перед сохранением

- Ломается ровно одно условие; остальные проходят.
- Любой ожидаемый результат трассируется к документу и разделу; ничего не взято по аналогии.
- В Steps нет `operator_id`, UI, двух способов auth; в Test data нет email, имён, UUID, дат.
- Дубли `covered_by` исключены; каждый criterion в кейсе или в `skipped`.
- ID уникальны, файлы новые.

## 11. Возврат

Одна строка JSON и ничего больше. Предупреждения из ответов инструментов (например, об устаревшем Atlassian V1) не пересказывать и в вывод не включать.

```json
{"status":"written","files":["test-cases/api/API-OPR-006.md"],"cases":[{"id":"API-OPR-006","technique":"BV","outcome":"REJECTED / TIME_WINDOW","ac":"SKY-2 AC1"}],"skipped":["<что> — <почему>"]}
```

или `{"status":"blocked","reason":"<одно предложение>"}`. `ac` — критерий, который закрывает кейс, или `null`.
