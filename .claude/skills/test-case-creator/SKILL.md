# Тест-кейсы

Тест-кейс — одна проверка с одним ожидаемым результатом, который можно
подтвердить по документации. Кейсы читают и исполняют другие люди, на них
ссылаются баг-репорты и прогоны, поэтому важны три вещи: ID стабилен и
уникален, ожидаемый результат трассируется к документу, данные конкретны
настолько, что кейс можно выполнить без догадок.

## 1. Определить модуль и фокус

Модули фиксированы. Новый модуль заводи только с согласия пользователя и
тогда допиши его в эту таблицу.

| Модуль | Что в нём | Основные источники |
|---|---|---|
| `auth` | Регистрация, login/logout/me, `401`/`403`, scoping по сессии, reviewer-or-owner чтение | `03-api-contract.md` §Authentication |
| `registry` | Pilots, aircraft: создание, чтение, списки, уникальность, производные currency/weight band, отказ при `mtom_grams` > 30 000 г; чтение оператора (`GET /operators/{id}`) | `01-data-model.md`; `03` §Registry; `06` §1.2, §2, §3 |
| `zones` | Справочник зон: список, одна зона, значения каталога | `03` §Reference data; `06` §4 |
| `flight-requests` | Create/get/list заявки, валидация полей (`flight_purpose`, окно), фильтры списка | `03` §Flight requests; `01` §FlightRequest, §Time handling |
| `gates` | 4 гейта, порядок и первый провал, тело `422`, `rule_reference`, `validate` (dry-run, паритет с `submit`) | `06` §1–§4, §6 с поправками `07`; `03` §422, §Gate pipeline, #13 |
| `state-machine` | Легальные/нелегальные переходы, `409`, дедлайн отмены, транзиентный `SUBMITTED`, `COMPLETED` | `02-state-machine.md`; `06` §5 |
| `review` | Approve/reject, `X-Reviewer-Id`, обязательный `note`, `ReviewAction`, `decided_*` | `03` §Reviewer; `01` §ReviewAction |
| `audit-log` | Запись `AuditLog` на переходы, append-only | `01` §AuditLog; `02` §Implementation note |
| `ui` | Портал оператора, очередь ревьюера, контракт `data-testid`, пикеры без пре-фильтрации | `04-frontend-spec.md` |

Пограничные случаи: overlap как условие гейта → `gates`; какие состояния
считаются в overlap → тоже `gates`; `409` на действие из неверного состояния
→ `state-machine`; чужой ресурс → `auth`; создание оператора
(`POST /operators`) — это регистрация → `auth`, не `registry`.

Фокус — то, что пользователь назвал внутри модуля: гейт, правило, переход,
`OQ-NN`, раздел тест-плана. Если модуль не ясен из запроса, спроси.

## 2. Прочитать источники

- Документация — `../skypermit/docs/`. Прочитай разделы модуля целиком, а
  также `05-open-questions.md` и `07-clarifications.md`: `05` — единственный
  источник статуса вопросов, `07` важнее `06` при расхождении.
- Тест-план модуля в `test-plans/`, если есть: риски и стратегия подсказывают
  уровень и приоритет кейсов.
- Реестр вопросов `test-plans/open-questions.md` — ID `OQ-NN`.
- Все существующие кейсы модуля — чтобы не создать дубль.
- Код `../skypermit` — **только oracle**, когда в документации пробел.
  Поведение кода не становится ожидаемым результатом. Если кейс на него
  опирается, укажи путь к файлу в Rationale и пометь, что это не документация.
- Значения из устаревших и непринятых источников (`OH-1` v1.4, `CR-1`) не
  используй ни в Expected result, ни в Test data.
- В `../skypermit` ничего не меняй.

## 3. Составить инвентарь проверок

До того как писать файлы, составь список атомарных проверок:

| Проверка | Doc ref | Уровень-роль | Ключевые данные |
|---|---|---|---|

Одна строка — один будущий кейс. Правила декомпозиции:

- **Атомарность.** Одна проверка — один ожидаемый результат. Ответ API
  целиком (код + тело) — это один результат. Состояние в БД после того же
  действия — уже другой кейс.
- **Границы.** Каждая сторона границы — отдельный кейс: на границе, на
  единицу ниже, на единицу выше (единица — шаг, в котором правило измеряется:
  грамм, минута, день).
- **Таблицы решений и матрицы** (роль × эндпоинт, состояние × действие):
  каждая ячейка с отдельным ожидаемым результатом — отдельный кейс.
- **Порядок гейтов:** кейс, где одновременно ломаются два гейта, проверяет
  только то, что `failing_gate` назван первым по порядку.

### Если запрос широкий («кейс на гейты»)

«Кейс на гейты» — это не один кейс: атомарных проверок там несколько
десятков (4 гейта × условия × стороны границ + порядок + `validate`). Один
большой кейс нарушит атомарность, а молча сгенерированные 50 файлов никто
не проверит. Поэтому:

1. Покажи инвентарь, сгруппированный по подобластям (для `gates` — по
   гейтам, плюс «порядок», «тело `422`», «`validate`»), с числом кейсов в
   группе и отметкой, какие из них будут `Blocked` из-за `OQ-NN`.
2. Предложи генерировать по одной группе за раз и спроси, с какой начать
   (или подтвердить всё).
3. Генерируй только подтверждённое.

Если инвентарь — до ~10 кейсов, сразу переходи к генерации.

### Дубли

Кейс с той же проверкой (то же правило, та же сторона границы, та же роль и
тот же эндпоинт) уже есть → не создавай новый, назови существующий ID в
отчёте. Если существующий кейс неверен, предложи правку, а не дубль.

## 4. Назначить ID

Формат: `{LEVEL}-{ROLE}-{NNN}`, например `API-OPR-001`.

| Часть | Значения |
|---|---|
| `LEVEL` | `API`, `UI`, `E2E`, `DB` — уровень, на котором наблюдается ожидаемый результат. Бери самый низкий уровень, где проверка возможна; тест-планы SkyPermit почти всё ставят на `API` |
| `ROLE` | `OPR` — оператор с сессией (свой или чужой ресурс); `REV` — запрос с `X-Reviewer-Id`; `ANON` — без сессии и без `X-Reviewer-Id`; `SYS` — без актора (seed, триггер, справочные данные) |
| `NNN` | Три цифры, сквозной номер для пары `LEVEL-ROLE` по **всем** модулям |

- `ROLE` — актор шага, который проверяется. Если заявку готовит оператор, а
  проверяется `approve` ревьюера, то роль — `REV`. Остальные участники
  перечисляются в Role(s).
- Номер: найди все файлы `test-cases/*/{LEVEL}-{ROLE}-*.md`, возьми
  максимальный `NNN` и прибавь 1. В пределах одного запуска выдавай номера
  подряд и держи их в инвентаре.
- Перед записью убедись, что файла с таким ID нет **ни в одном** модуле:
  номер сквозной, а папки разные.
- ID не переиспользуются и не перенумеровываются, даже если кейс перенесён
  в другой модуль или удалён.

## 5. Написать кейс

Путь: `test-cases/{module}/{ID}.md`. Заголовки полей — на английском, текст —
на русском. Идентификаторы из документации (сущности, поля, статусы,
эндпоинты, коды гейтов) не переводи. Порядок полей фиксирован:

```markdown
# {ID}: <что проверяем, одной строкой>

- **ID:** {ID}
- **Doc ref:** `<файл>` §<раздел>[; `<файл>` §<раздел>][; OQ-NN]
- **Role(s):** <актор шага; кто ещё участвует в предусловиях>

## Preconditions
- <состояние системы и данных до шага; подготовка через API, если она возможна>

## Steps
1. <действие: метод, путь, заголовки, тело — ссылкой на Test data>

## Expected result
<один наблюдаемый результат: код ответа и значимые поля тела, или состояние,
или то, что видно в UI. Каждое утверждение трассируется к Doc ref.>

## Rationale
<зачем кейс: какое правило и какая сторона границы, какой риск из тест-плана
(`R#`), какая техника (граничные значения, таблица решений, переходы
состояний). Опору на код помечай: «код, не документация: `<путь>`».>

## Test data
| Параметр | Значение | Почему это значение |
|---|---|---|
| <поле> | <конкретное значение> | <граница / класс эквивалентности> |

## Status
Untested
```

### Steps и Preconditions

- Подготовка — в Preconditions, в Steps только проверяемое действие (обычно
  один–три шага).
- Состояния, до которых можно дойти через API, готовь через API. Если нужна
  прямая запись в БД (например, неактивная зона, повышение
  `authorisation_level`), так и пиши: эндпоинта для этого нет.

### Test data

- Значения конкретные и стоят на границе: `mtom_grams = 900`, а не «лёгкий
  дрон»; длительность `15 мин`, `14 мин`, а не «короткое окно».
- Время, зависящее от «сейчас», задавай относительно момента шага:
  `T` = время отправки запроса (UTC), `window_start = T + 6 ч 00 мин`. Для
  правил с точностью до минуты указывай запас и точность явно. Абсолютные
  даты используй там, где правило от «сейчас» не зависит.
- Справочные данные (зоны) — из `06-business-rules.md` §4 с кодом зоны.
- Для каждого значения напиши, почему выбрано именно оно.

### Ожидаемый результат не определён

Если ответ зависит от вопроса, не решённого по `05-open-questions.md`, или от
противоречия в документах:

- Expected result: «Не определено — OQ-NN» и коротко, между чем выбор
  (например, «`409` или `422 TIME_WINDOW`»). Не подставляй ответ по аналогии
  с похожими эндпоинтами и не бери его из кода.
- Status: `Blocked — OQ-NN`.
- Вопроса нет в `test-plans/open-questions.md` → добавь его туда по правилам
  реестра (следующий номер, обе стороны с цитатами, статус «Кандидат») и
  сошлись на новый ID.

Часть кейса, которая определена (например, что состояние не изменилось),
выноси в отдельный кейс со статусом `Untested`, если это осмысленная проверка
сама по себе.

### Status

| Значение | Когда |
|---|---|
| `Untested` | По умолчанию для каждого нового кейса — к выполнению ещё не приступали |
| `Passed` | Фактический результат полностью совпал с ожидаемым, дефектов нет |
| `Failed` | Поведение отличается от ожидаемого; рядом ставь ссылку на баг-репорт: `Failed — <ссылка>` |
| `Blocked` | Выполнить невозможно из-за другого дефекта или внешних факторов: `Blocked — <ID бага / OQ-NN>` |
| `Skipped` | Сознательно не выполнялся в этом цикле (фича вырезана или отключена): `Skipped — <причина>` |

Новые кейсы получают только `Untested` или `Blocked — OQ-NN`. `Passed`,
`Failed` и `Skipped` ставятся по итогам прогона, не при генерации.

## 6. Проверить перед сохранением

- Каждый кейс — одна проверка и один ожидаемый результат.
- ID уникален во всём `test-cases/`, формат `{LEVEL}-{ROLE}-{NNN}`, имя файла
  совпадает с ID, кейс лежит в папке своего модуля.
- Порядок и написание полей ровно как в шаблоне.
- Каждое утверждение в Expected result трассируется к Doc ref; ничего не
  взято по аналогии; опора на код помечена путём.
- Test data конкретны, граничные значения стоят на границе, у каждого есть
  обоснование.
- Нерешённое — «Не определено — OQ-NN» и `Blocked — OQ-NN`; ID есть в реестре.
- Нет значений из `OH-1` v1.4 и `CR-1`.
- Нет дублей существующих кейсов.

## 7. Отчитаться

В ответе пользователю: модуль, число созданных кейсов, список `ID — название`
(для большой партии — по группам), какие кейсы `Blocked` и по каким `OQ-NN`,
новые вопросы в реестре, найденные дубли. Сами кейсы в чат не дублируй — они
в файлах.
