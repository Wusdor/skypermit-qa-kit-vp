# Прогон Postman-коллекции и отчёт по кейсам

Вход:

$ARGUMENTS

JSON-объект: `key`, `collection_id`, `environment_id` (uid Postman вида `<owner>-<uuid>`).
Если чего-то нет — ничего не делать и вернуть
`{"status": "error", "reason": "<чего не хватает>"}`.

## Жёсткие правила

- **Только по явному «запускай».** Запускать, только если пользователь в этой беседе
  прямо сказал запускать эту коллекцию («запускай» на гейте оркестратора) либо вручную
  вызвал `/postman-cli-run`. Иначе вернуть
  `{"status": "error", "reason": "нет явного «запускай» от пользователя"}`.
  Каждый прогон против `skypermit.vercel.app` оставляет постоянные данные.
  Дополнительная защита — правило `ask` на `Bash(postman collection run:*)`
  в `.claude/settings.json`.
- Один прогон на вызов, без повторов при падении. Не менять коллекцию, environment,
  песочницу, настройки и приложение, чтобы тест прошёл. Блокировки не обходить:
  при ошибке сети, TLS или логина — `{"status": "error", ...}` с первой строкой
  ошибки.
- Значения секретных переменных environment не выводить ни в отчёт, ни в чат.
- Результат берётся только из вывода CLI. Статус кейса никогда не выводится из его
  названия или из того, что «должно» произойти.

## Перед прогоном

1. `getEnvironment`: прочитать `baseUrl` (значения `secret`-переменных не читать и не
   показывать).
2. `getCollection`: перечислить имена запросов. **Запрос кейса** — имя, подходящее под
   `^([A-Z]+(?:-[A-Z0-9]+)*-\d+):\s`; группа 1 — ID кейса (`API-OPR-001`).
   Имя с префиксом `SETUP: ` — setup-запрос. Остальное игнорируется. ID хранить в
   порядке коллекции.
3. Если запросов кейса нет вообще — не запускать, вернуть
   `{"status": "error", "reason": "нет запроса «<ID кейса>: …» — результатам не к чему привязаться"}`.

## Прогон

```bash
mkdir -p api-automation/runs
postman collection run <collection_id> -e <environment_id> --disable-unicode -x \
  > api-automation/runs/<key>-<YYYYMMDD-HHMMSS>.log 2>&1
```

`-x` оставляет код выхода 0 при падающих тестах, чтобы упавший тест не путался со
сломанным прогоном. `--output` доступен только в Enterprise, поэтому отчётом служит
лог. Затем прочитать лог через `Read`.

Если по логу CLI не смог стартовать (нет логина, неверный API-ключ, не найдены
коллекция/environment, ошибка сети или TLS), вернуть
`{"status": "error", "reason": "<первая строка ошибки>"}`. При проблеме с логином
добавить `"hint": "! postman login --with-api-key <ключ>"` (ключ самому не подставлять).
Прогон не повторять.

## Разбор лога

С `--disable-unicode` CLI печатает по блоку на запрос:

```
<путь папки> <имя запроса>

  POST https://… [<код> <текст>, <размер>, <время>]    ← или [errored] и причина на следующей строке
  Pass  <имя ассерта>                                  ← пройденный ассерт
  3. <имя ассерта>                                     ← упавший ассерт; 3 — строка в таблице failures
```

После итоговой таблицы идёт таблица failures. Каждая строка — `<n>.  <AssertionError|Error|…>  <имя ассерта>`,
затем строки с деталями и `inside "<путь папки> / <имя запроса>"` (или только имя запроса).

По каждому запросу: HTTP-код (или `errored`), пройденные ассерты, упавшие ассерты с
деталями из таблицы failures (сопоставлять по `n`).

## По кейсам

Сгруппировать запросы кейсов по ID. Кейс:

- `passed` — все его запросы выполнились (не `errored`) и все ассерты прошли.
- `failed` — любой запрос `errored` или любой ассерт упал. В `message` каждый провал
  как `<имя запроса> — <имя ассерта>: <детали>`, через `; `.
- `skipped` — запрос кейса есть в коллекции, но в логе его нет (прогон остановился
  раньше). В `message` так и сказать.

SETUP-запросы в `results` не попадают. Если какой-то из них упал, добавить его провалы
в `errors` как `SETUP: <имя запроса> — <ассерт>: <детали>` и приписать префикс
`setup failed — ` к `message` каждого `failed`/`skipped` кейса, чтобы причина была
видна.

## Вернуть

Один блок `json` и ничего больше. Значения `status` в `results` — `passed` / `failed` /
`skipped`; общий `status` — `completed` или `error`.

```json
{
  "status": "completed",
  "key": "SKY-2",
  "results": [
    {"case_id": "API-OPR-001", "status": "passed", "message": ""},
    {"case_id": "API-OPR-002", "status": "failed", "message": "API-OPR-002: Получить заявку — state = REJECTED: expected 'APPROVED' to deeply equal 'REJECTED'"}
  ],
  "summary": {"passed": 1, "failed": 1, "skipped": 0},
  "log": "api-automation/runs/SKY-2-20261119-171500.log",
  "errors": []
}
```
