# Закрыть непокрытые бизнес-правила

Цель — чтобы у каждого `rule_reference` из `../skypermit/docs/06-business-rules.md`
§6 (с поправками `07-clarifications.md`) был хотя бы один проверенный
тест-кейс. Пайплайн: список дыр → один кейс на правило через
`test-case-creator` → проверка каждого кейса субагентом `tc-verifier` →
JSON-итог.

## 1. Дыры

Список ниже выдал `scripts/uncovered-rules.mjs` (аргументы: `$ARGUMENTS`):

!`node scripts/uncovered-rules.mjs $ARGUMENTS`

Это единственный источник списка правил. `06` целиком не перечитывай:
скрипт уже применил поправки `07`, развёл общую цитату `ZC-2026.1 §2` на
`AIRCRAFT` и `ZONE`, приложил текст правила и открытые вопросы из
`test-plans/open-questions.md`. Нужные детали `test-case-creator` прочитает
сам в своих разделах.

- Строка начинается с `ОШИБКА` → покажи её пользователю и остановись.
- `gaps_found: 0` → сразу переходи к разделу 5 с пустыми `results`.
- Обрабатывай только показанные правила (их уже ограничил `max-rules`).

## 2. Создать кейс на каждое правило

Правила обрабатывай по одному, в порядке вывода. Для каждого вызови скил
`test-case-creator` (Skill) и передай в аргументах:

- модуль: `gates`; для `REGISTRATION` — `registry`;
- фокус: gate, `rule_reference`, условие, текст правила и строку «применимо
  к», если она есть, — дословно из вывода скрипта;
- ограничения ниже.

Ограничения для кейса, с причинами — передай их вместе с причинами:

- **Ровно один кейс:** нарушение правила значением у самой границы (на шаг
  за порогом: 6 ч − 1 мин, 241 мин, 61 день, зона класса выше рейтинга и
  т. п.). Задача прогона — закрыть дыру, а не построить полную матрицу
  границ. Инвентарь в 1 строку подтверждения не требует.
- **Цитата в `## Expected result` в каноничной форме:**
  `failing_gate: <GATE>` и `rule_reference: "<ref>"` (для `REGISTRATION` —
  только `rule_reference: "<ref>"`). Скрипт ищет покрытие только в этом
  разделе и только по паре (gate, ref). Кейс, где цитата есть лишь в Doc ref
  или Rationale, останется дырой.
- **Если по правилу есть открытый вопрос** (в выводе `открытые вопросы:
  OQ-NN`) и он делает ответ неопределённым: Expected result «Не определено —
  OQ-NN», а оспариваемая сторона всё равно названа той же парой. Например:
  «`422`, `failing_gate: ZONE`; `rule_reference` не определено — OQ-02:
  `rule_reference: "ZC-2026.1 §4"` или другая цитата». Status
  `Blocked — OQ-NN`. Так кейс честно помечен как Blocked, а скрипт всё равно
  видит, что правило адресовано.
- **ID** выдаются подряд в пределах прогона по правилам `test-case-creator`.
  Держи список выданных ID: он нужен для проверки и итога.

Не плоди дубли: если `test-case-creator` нашёл существующий кейс с той же
проверкой, но без каноничной цитаты, предложи пользователю дописать в него
цитату, а не создавать новый.

## 3. Проверить каждый кейс

На каждый созданный ID вызови субагента `tc-verifier` (Agent,
`subagent_type: tc-verifier`) с одним ID в запросе. Проверки независимы —
запускай их параллельно, одним сообщением.

| Вердикт | Что делать |
|---|---|
| **соответствует** | Кейс остаётся |
| **не соответствует** | Одна попытка: исправь кейс по замечаниям верификатора (Edit), сохранив каноничную цитату, и снова вызови `tc-verifier`. Снова «не соответствует» → удали файл (`rm test-cases/<module>/<ID>.md`; он ещё не закоммичен, команда запросит разрешение у пользователя), в итоге `file: null`. Номер ID сгорел — переиспользовать его нельзя, отметь это в отчёте |
| **документация молчит** | Кейс остаётся, но должен быть `Blocked — OQ-NN` с «Не определено — OQ-NN» в Expected result. Если в нём стоял конкретный результат, приведи его к этому виду по правилам `test-case-creator` (цитату-пару сохрани). OQ должен быть в `test-plans/open-questions.md` — если его нет, добавь по правилам реестра. Запись идёт в `open_questions` итога |

После вердикта «соответствует» кейс не правится. Любая правка после
проверки — в том числе по необязательным замечаниям верификатора и при
приведении к виду Blocked по строке «документация молчит» — требует
повторного `tc-verifier` для этого кейса. В итог идёт вердикт последней
проверки. Почему «не
соответствует» не остаётся в `test-cases/`: на кейсы ссылаются прогоны и
баг-репорты, и неверный ожидаемый результат хуже отсутствующего.

## 4. Контроль

Запусти `node scripts/uncovered-rules.mjs all <gate из аргументов, если был>`.
Каждое правило, по которому кейс остался в `test-cases/`, должно пропасть из
списка дыр. Если не пропало, цитата в Expected result не в каноничной
форме: поправь её и запусти скрипт ещё раз. Не получилось — отметь в
отчёте.

## 5. Итог

Выполни `git status --short` и покажи вывод. Не коммить и не пушь:
пользователь коммитит сам после ревью.

Затем — короткий отчёт (что создано, что удалено, сгоревшие ID, правила,
оставшиеся дырами после контроля) и JSON-итог в блоке ```json строго в этой
форме:

```json
{
  "rules_checked": 13,
  "gaps_found": 13,
  "results": [
    {
      "rule_reference": "TSD-4 §3",
      "gate": "TIME_WINDOW",
      "case_id": "API-OPR-001",
      "verdict": "соответствует",
      "file": "test-cases/gates/API-OPR-001.md"
    }
  ],
  "open_questions": [
    {
      "oq_id": "OQ-02",
      "rule_reference": "ZC-2026.1 §4",
      "case_id": "API-OPR-002",
      "question": "цитата для неактивной зоны не подтверждена (05 №5)"
    }
  ]
}
```

- `rules_checked`, `gaps_found` — из первой строки вывода скрипта в разделе 1.
- `results` — по одной записи на каждый созданный кейс (включая удалённые).
  `verdict` ∈ `соответствует` | `не соответствует` | `документация молчит`.
  `file` — путь от корня кита или `null`, если файл удалён.
- `open_questions` — кейсы с вердиктом «документация молчит»: ID вопроса из
  реестра и одна строка о сути пробела.
